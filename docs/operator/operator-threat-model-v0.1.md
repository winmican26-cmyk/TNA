# TNA Operator CLI & Deployment Academy v0.1 Threat Model

Status per category: MITIGATED, PARTIALLY MITIGATED, or NOT MITIGATED (by design or by scope).

| # | Threat | Status | Detail |
|---|---|---|---|
| 1 | Operator credential theft | PARTIALLY MITIGATED | credentials live only in environment variables referenced by name from a profile file, never written to disk by this CLI; theft of the underlying env var is outside this CLI's control (same posture as every prior TNA subsystem's bearer-token model) |
| 2 | Overprivileged operator | PARTIALLY MITIGATED | the closed 4-role model and `COMMAND_MIN_ROLE` table bound what a given profile can even attempt; the actual privilege ceiling is still whatever bearer token the profile references — a `viewer`-role CLI profile paired with an admin-token env var is a real misconfiguration this CLI does not detect |
| 3 | Self-approval | MITIGATED | `hold approve` refuses when the resuming operator's profile name matches the action's `created_by`; Gate's own approver-role separation (Volume 1, unchanged) covers Gate-level approvals |
| 4 | Wrong-tenant action | PARTIALLY MITIGATED | `--tenant` must be supplied explicitly for every tenant-scoped command; `tenant offboard` additionally requires `--confirm <exact-id>`. Other mutating tenant-scoped commands (suspend, tool enable/disable) do not require the extra confirmation step |
| 5 | Fat-finger offboarding | MITIGATED | `--confirm <exact-tenant-id>` plus mandatory `--reason`, tested in `tests/operator/cli-client-gateway.test.ts` |
| 6 | Unsafe restore | NOT APPLICABLE (out of scope this pass) | no `tna deployment restore` command exists yet — Volume 9's own `npm run tna:restore` safeguards are unchanged and untouched |
| 7 | Secret output leakage | MITIGATED | `redactDeep()` applied to every command's output by default; proven in `tests/operator/operator-units.test.ts` and the real-token-absence assertions in `tests/operator/cli-client-gateway.test.ts` |
| 8 | Incident bundle leakage | MITIGATED | same redaction applied before packaging; proven directly (admin token absent from a real collected package) |
| 9 | Cross-tenant support bundle | MITIGATED | `--tenant` scopes `client_gateway_health`; the platform client is bound to one deployment tenant by construction |
| 10 | Doctor mutation | MITIGATED (by construction) | `doctor.ts` issues only GET requests; no test currently exercises this negatively (see requirement matrix) |
| 11 | CLI TLS downgrade | MITIGATED | a non-`https://` endpoint is refused unless `devMode: true` is explicit in the profile |
| 12 | Profile confusion | PARTIALLY MITIGATED | each profile names its own endpoints; there is no cross-profile state leakage, but this CLI does not print the target deployment/tenant before every consequential operation (section 83 not fully implemented — see requirement matrix) |
| 13 | Command injection | MITIGATED (by construction) | the CLI never shells out to construct dynamic commands; all subsystem calls are structured HTTP JSON requests |
| 14 | Malicious MCP server | NOT MITIGATED (by design — inherited from Volume 10 §116) | unchanged; this CLI observes the same interface boundary Volume 10 already documented |
| 15 | Lab destructive escape | MITIGATED | `assertLabModeEnabled`/`assertInsideLabWorkspace` (real-path resolution, not string-prefix matching); tested in `tests/academy/lab-safety.test.ts` |
| 16 | Lab production-data access | MITIGATED | `academyLabWorkspaceRoot()` is a fixed path under `academy/.lab-state/`, never a deployment data directory |
| 17 | False lab success | MITIGATED | every lab verifier performs real assertions against real TNA state; `tests/academy/lab-verifier.test.ts` proves every implemented lab's `passed` field is backed by ≥1 real check |
| 18 | Operator bypass via DB | NOT APPLICABLE | this CLI has no direct database access path at all — section 7 |
| 19 | Stale health | PARTIALLY MITIGATED | every `doctor`/`status`/`go-live assess` call re-queries live endpoints; there is no CLI-side caching to go stale, but a caller could act on an old printed result |
| 20 | Stale config | NOT MITIGATED (out of scope this pass) | no CLI command inspects config-hash drift over time |
| 21 | Incident misclassification | PARTIALLY MITIGATED | `doctor`'s PASS/WARN/FAIL mapping follows the accepted mandatory/optional readiness distinction; it is a deterministic mapping, not a judgment call, but no independent audit of the mapping's correctness exists beyond the go-live unit tests |
| 22 | Evidence corruption | NOT MITIGATED (by design) | this CLI never repairs Ledger corruption automatically; `go-live assess` reports NO_GO and stops there |
| 23 | Forged Academy completion (assessment) | MITIGATED | `assessLevel()` computes the knowledge score itself from raw submitted answers and reads lab status only from the runtime-owned progress store; a learner cannot submit a pre-computed score or an asserted PASSED status. Tested: `tests/academy/assessment.test.ts` ("cannot forge lab PASS", "cannot forge a knowledge score"); real-process proof in `tests/operator/cli-academy.test.ts` |
| 24 | Forged lab PASS | MITIGATED | the only code path that can write a PASSED lab status is `recordLabAttempt`, called only after actually running the real verifier; a hand-written progress row claiming PASSED with no `verified_at`/`evidence_refs` is downgraded to FAILED before it can count (the exact bug this defense was designed to catch was found and fixed during this closure — see the proof-of-work). Tested: `tests/academy/assessment.test.ts` |
| 25 | Forged assessment score | MITIGATED | same mechanism as #23 — the CLI's `academy assessment` command accepts only `{question_id, answer}` pairs, never a `score` field; extraneous forged fields on a submitted answer object are structurally ignored (`KnowledgeAnswer` only reads `question_id`/`answer`). Tested: `tests/academy/assessment.test.ts` |
| 26 | Question-answer leakage | MITIGATED | `toLearnerFacing()` strips `correct_answer` via destructuring before any question ever reaches CLI output; tested for every one of the 120 real questions in `tests/academy/question-bank.test.ts`, and against the real CLI's raw stdout text in `tests/operator/cli-academy.test.ts` ("`academy assessment --questions` never exposes correct_answer") |
| 27 | Learner-submitted `correct_answer` (attempting to smuggle a self-supplied correct_answer field to influence grading) | MITIGATED | grading in `scoreKnowledge()` always looks up `correct_answer` from the loaded, sealed question bank (`questionsForLevel()`) — it is never read from the learner's submitted answer object at all, so a learner-supplied `correct_answer` field has no code path into the score. Tested: `tests/academy/assessment.test.ts` ("cannot forge a knowledge score") |
| 28 | Destructive-lab path escape (`../` traversal, absolute external path) | MITIGATED | `assertInsideLabWorkspace` resolves the real path and verifies containment, never string-prefix matching. Tested: `tests/academy/lab-safety.test.ts` |
| 29 | Symlink/junction escape | MITIGATED | same `assertInsideLabWorkspace` real-path resolution defeats a symlink pointing outside the workspace. Tested: `tests/academy/lab-safety.test.ts` — history: the original Windows symlink-escape test was initially SKIPPED (elevation required for a true symlink on Windows); that skip was rejected as acceptable closure evidence, an NTFS junction technique (`fs.symlinkSync(..., 'junction')`, which needs no elevation) was substituted, and the test now executes for real on every platform — 0 skips |
| 30 | Production path targeted by lab reset (`npm run academy:reset`) | MITIGATED | `academy-reset.ts` calls the same `academyLabWorkspaceRoot()`/`assertInsideLabWorkspace()` primitives as every lab — there is no argument or environment variable by which a caller can point it at an arbitrary path; it always resolves to the fixed Academy lab workspace. Covered by the same `lab-safety.test.ts` path-safety proof |
| 31 | Academy process leakage (MCP fixture, packaged client gateway, operator CLI child processes) | MITIGATED | every process-spawning lab (`lab-07`, `lab-08`, `lab-10`, `lab-13`, `lab-15`) reports the exact pid(s) it spawns; `tests/academy/process-cleanup.test.ts` verifies each specific pid is dead after the lab completes (by exact pid, not a racy system-wide command-line scan). `lab-13`/`lab-15`'s direct spawned child is additionally structurally guaranteed dead by `spawnSync`'s blocking semantics. `lab-06`/`lab-11` (the destructive labs) spawn no child process at all, verified structurally (no `node:child_process` import) |
| 32 | Academy completion granting production authority (TNA-69) | MITIGATED | `assessment.ts`/`progress-store.ts` import nothing from `config.ts`, `roles.ts`, or `http-client.ts` — structurally no code path from an assessment result to an `OperatorProfile` or any production authority record. Tested structurally in `tests/academy/assessment.test.ts` ("never touches any OperatorProfile, role, tenant, Gate, credential, or policy-binding state") |
| 33 | Cross-learner state contamination | MITIGATED | every progress-store lookup is scoped by `learner_id`; a different `learner_id` sharing the same underlying SQLite file sees zero of another learner's entries. Tested against a real, separate CLI process pair in `tests/operator/cli-academy.test.ts` ("one learner's persisted Academy progress is never visible to a different learner") |
| 34 | Cross-tenant lab evidence | NOT APPLICABLE | Academy labs never write to any real tenant's data — each lab that touches `ClientStore`/`PlatformStore` constructs its own disposable in-memory (`:memory:`) or lab-workspace-confined store per run; there is no shared store between a lab run and any real tenant, so cross-tenant lab evidence cannot occur by construction. `lab-10-tenant-isolation` itself additionally proves cross-tenant isolation *within* its own synthetic two-tenant scenario |
| 35 | Production credentials appearing in lab state | MITIGATED (real finding fixed during this closure) | `lab-13-incident-triage` originally spread the invoking shell's entire `process.env` into its spawned CLI child, which would have forwarded any real production credential env var present in that shell (e.g. a real operator's `TNA_CLIENT_ADMIN_TOKEN`) even though the lab's target gateway is unreachable and the credential is never actually transmitted. Fixed: the lab now strips every secret-shaped env var (reusing `redact.ts`'s own `SECRET_KEY_PATTERN`) before building the child's environment. Tested: `tests/academy/process-cleanup.test.ts` (a decoy secret-shaped env var is set on the test process and the lab is proven to still function correctly without it reaching the child) |
| 36 | Stale lab evidence counted as current success | NOT MITIGATED (out of scope this pass) | a lab verified once remains PASSED in the progress store indefinitely; there is no re-verification-on-expiry or evidence-freshness policy for v0.1. If the underlying TNA code changes after a lab was verified, the stored PASSED status is not automatically re-checked. This is an honest, documented residual limitation, not a claimed mitigation |

## Human error as a threat category (TNA-65)

Volume 11 explicitly treats operator mistakes as a threat class, not an insult: the role model, reason
requirements, wrong-tenant confirmation, and self-approval guard all exist because a well-intentioned
human operator can make an incorrect, rushed, or ambiguous decision. None of these mechanisms assume
malice — they assume competence under time pressure.

## Training does not grant authority (TNA-69)

Academy progress (labs, question banks, assessments) is tracked entirely locally under `academy/` and
has no code path that reads or writes an `OperatorProfile`'s role. Completing every lab in this volume
changes nothing about what a real operator profile is permitted to do in production.
